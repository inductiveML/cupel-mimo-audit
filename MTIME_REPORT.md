# MTIME REPORT: does the MiMo `mtime_scope` leak help agents?

**Date:** 2026-10-19/20 (VPS, 4 CPU / 7 GB).
**Inputs:** Phase-1 artefacts (see `PHASE1_REPORT.md`; read-only). **Outputs:** `results/`, `scripts/`, `runs/` in this folder.
Every number below is taken from a file in `results/`. The full tables are generated by `scripts/report_tables.py` → `results/report_tables.md`. Inferences are labelled as such.

---

## 1. Verdict (plain English)

1. **The signal is real and strong offline.** For the 218 flagged tasks where our tracked-file reconstruction is reliable, sorting files by mtime (newest first) puts an upstream-fix file at rank 1 in **92%** of the 75 tasks where the upstream fix could be anchored (hit@1 0.92, 95% CI 0.88–0.96), and in the top 3 in all of them. Precision@3 is 0.79. Lexical matching of the issue text against file paths reaches only 0.23 hit@1 / 0.56 hit@5, and a random ranking 0.03 / 0.11 (`results/stepA_metrics.json`).
2. **A cheap agent that is not told about the leak does not use it, and it does not measurably help.** We ran 73 paired tasks with `deepseek/deepseek-v4.1-flash-1017`: the same task and image, once with the original timestamps (ORIG) and once with every mtime under the repo set to the epoch (NORM).
   - Pre-registered primary set (30 pairs): ORIG 21/30 vs NORM 20/30. Discordant pairs 4:3, exact McNemar **p = 1.0**, paired difference **+3.3 pp (95% CI −13.3 to +20.0)**.
   - All 73 pairs: 50 vs 47, discordant 9:6, p = 0.61, **+4.1 pp (−5.5 to +15.1)**.
   - In 146 runs and 3,488 commands, **no agent ever sorted or filtered files by time.** One ORIG command matched the pre-registered `stat` rule, but it was `stat -c '%n %s'`, which prints name and size, not time. Agents did hunt for git leftovers (`git fsck`, `git log --all`, `git reflog`) in 21 ORIG and 23 NORM runs.
   - Agents opened a late-cluster file before their first edit in 71/73 ORIG and 72/73 NORM runs, and edited a late-cluster file in 89% vs 88% of runs. **In other words, the issue text alone already leads the agent to the files the mtime leak would reveal.** (Inference from the observed run data.)
3. **Severity:** the leak is **I2** (it reveals scope, not the solution) and **R4** (ordinary tool use: `ls -t`, `find -newer`). We found no evidence that it materially raises solve rate for an uninformed agent, so our measurement supports **Low**, not Medium. Two caveats: (a) the study can only rule out large effects. With n = 30 even a +23 pp effect would be detected only 73% of the time. With n = 73 the effect detectable with 80% power is about +15 pp. (b) The offline numbers show that an agent or policy that learns to look at mtimes (for example through RL on these images) would get a near-perfect file-localisation oracle. "Low" is about present-day exploitation by uninformed agents, not about the information content, which is high. An RL-trained policy that discovers `ls -t` is the plausible route to Medium. That is untested here.

## 2. Method

### 2.1 Step A: offline signal strength (no Docker, no agent) — `scripts/stepA.py`
- **Tasks:** the 256 phase-1 tasks flagged `mtime_scope` (`tier_a.jsonl`), plus the 43 unflagged tasks as a contrast.
- **Candidates:** "tracked" regular files under the task `cwd`. Phase 1 used the HEAD tree, which is not stored offline. We rebuilt it from the manifests (`scripts/tracked_proxy.py`: files under cwd minus `.git/`, `node_modules`, venvs, caches, `*.egg-info`, `*.pyc`, …). The proxy agrees with phase-1 `n_tracked` within ±5% **and** contains every phase-1 late file in **257/299** tasks (**218/256 flagged**; exact count match in 170). Main numbers use those 218. "All flagged" (proxy as-is) is reported as a sensitivity check and gives the same picture.
- **Ties:** the bulk cluster shares mtimes. All rankers are scored **analytically under uniformly random tie-breaking**: the expected number of relevant files in the top k, and P(hit@k) from the hypergeometric distribution of the partially included tie group.
- **Reference sets (always restricted to files that exist at base):**
  - `R_fix`: upstream fix files. Phase-1 anchors (13 tasks) were extended by re-running a copy of phase-1 `mtime_precision.py` over the 196 flagged tasks it had not tried (anonymous GitHub API, background). **75 more anchored**, of which 61 had the late set exactly equal to the fix (mean precision 0.915, recall 0.964; `results/mtime_precision_ext.json`). That gives 88 anchored tasks in total, 75 of them proxy-OK. Anchored tasks may be biased toward simple single-commit fixes.
  - `R_test`: files touched by `test_patch` (130 proxy-OK flagged tasks; the rest only add new test files). This is a **proxy, not the gold patch**. The late cluster contains test files *because* the upstream commit touched them, so R_test hits are partly mechanical.
  - `R_src_proxy`: non-test code files whose stem matches a `test_patch` file after stripping test affixes (`test_foo.py`→`foo.py`, `foo_test.go`→`foo.go` in the same dir, `Foo.test.ts`→`Foo.ts`, …) (91 tasks).
  - `R_agent`: files changed by passing Step-B agent patches, both conditions (55 proxy-OK tasks). This is a weak reference. It is independent of mtime because no agent used mtimes (§3.2).
- **Baselines:** uniform random; size descending and size ascending; BM25 of the `problem_statement` over path and basename tokens (paths only: file contents are not in the manifests); and mtime with BM25 as tie-breaker.
- **Metrics:** P@k, R@k, hit@k for k = 1, 3, 5, 10, with bootstrap 95% CIs over tasks (2,000 resamples).

### 2.2 Step B: paired agent A/B — `scripts/stepB.py`, `scripts/agent.py`
Pre-registered in `results/stepB_plan.md` before any agent run, with four dated amendments (§2.3).
- **Selection** (`scripts/stepB_select.py`, seed 1019): pool = flagged ∩ proxy-OK ∩ compressed image ≤ 1.2 GB = 83 tasks. 135 flagged tasks were excluded only for image size (disk/time).
  - "Strong" stratum (37): 1 to 10 late files, ≥ 1 late source file, and late cluster ∩ R_test ≠ ∅ or anchored R_fix.
  - "Random" stratum: the other 46.
  - Seeded order within each stratum, interleaved strong, strong, random.
  - **Primary = first 20 valid strong + first 10 valid random.**
- **Grader:** `test_patch` itself ships `mimo_test_command.sh` (sometimes with a base64 build-env tarball). After the agent finishes, we `git apply` `test_patch` (from `/tmp`, so the agent never sees it) and run `test_command` with `verifier_timeout_sec`. **Pass iff the patch applies and the command exits 0.** The test patch applied in 146/146 runs.
- **Validation:** in fresh containers with no changes, the grader had to fail in both ORIG and NORM. 74 tasks were validated. Exclusions:
  - 1 task, 001939: base grader exceeded 900 s.
  - 1 task, 001495, was wrongly excluded by a regex bug and then reinstated (Amendment 2).
  - No task passed at base, and normalization alone never changed a grade.
  - **There is no gold patch, so no gold-pass check was possible.** Unsolvable tasks only add fail/fail pairs.
- **Conditions:** one fresh container per run (`--network none --memory 2g --cpus 1.5`, named `mtime_*`).
  - NORM: `find <cwd> -xdev -exec touch -h -d @0 {} +` (all files, dirs and symlinks, including `.git`). Verified afterwards: `find <cwd> -newermt @1` returned 0 entries in 73/73 NORM runs.
  - ORIG: the same `find … -exec true {} +` (a no-op).
  - Condition order per task was set by a seeded coin.
- **Agent:** a mini-swe-agent-style loop written for this study.
  - One bash command per turn, run via `docker exec … timeout 120 bash -lc` in `cwd`; output truncated to 6,000 chars.
  - Step cap 40; per-run cost cap $0.15.
  - Model `deepseek/deepseek-v4.1-flash-1017` on OpenRouter, provider pinned to `deepseek` with no fallbacks; temperature 0, seed 7.
  - The prompt is identical in both conditions and never mentions timestamps.
  - Host-side `git diff`/`ls-files --others` after each step detects the first edit; these checks are not counted as agent steps.
- **Analysis** (`scripts/stepB_analyze.py`, `scripts/power.py`): exact McNemar; paired bootstrap (10,000 resamples) for the pass difference and for secondary metrics. mtime classification is recomputed from the saved trajectories, so the same rule applies to every run. `scripts/audit_mtime_cmds.py` adds a broad keyword audit for false negatives.

### 2.3 Protocol changes (all recorded in `results/stepB_plan.md`)
1. **Amendment 1, after pilot v1 (4 runs, 0 passes, $0.054; archived in `results/pilot_v1/`, excluded):**
   - parse the model's native DSML tool-call markup as a command;
   - fix a `stat` regex false positive;
   - add one budget sentence to the system prompt ("at most 40 commands …").
   Pilot tasks were re-run from scratch, as pre-registered.
2. **Amendment 2:** the "needs network" exclusion regex was case-insensitive, so `ENOTFOUND` matched `ServiceNotFound`, and task 001495 was wrongly excluded. The regex was fixed and the task run. The primary set is the one the corrected rule selects. The 30 tasks as originally run are reported as a sensitivity check: 21 vs 19, p = 0.69.
3. **Amendment 3, after an interim look (labelled as such):** an extension beyond the pre-registered 30, with a fixed stopping rule (end of pool/schedule, $4.50, or 07:30Z). It ended when the interleaving schedule ran out at 06:15Z: all 37 strong tasks processed, 9 of 46 random tasks never reached.
4. **Amendment 4:** the classifier is case-sensitive and ignores heredoc bodies. Go source `os.Stat(` written via heredoc had matched before.

## 4. Threats to validity
- **No gold patch.** `R_fix` exists only for 88 anchored tasks (75 in the main set) and may favour simple fixes. `R_test` and `R_src_proxy` are proxies, and R_test is mechanically linked to the late cluster. `R_agent` is circular for "files agents find" but independent of mtime. There was no gold-pass validation, so some fail/fail pairs may be unsolvable tasks.
- **Tracked-file proxy.** HEAD trees were not available offline. 38 flagged tasks were dropped from the main Step A numbers; the sensitivity analysis including them agrees.
- **What Step B measures.** It measures the effect of the leak's *presence* on an agent not told about it. It does not measure an agent that knows to look (the offline numbers are the upper bound for that) or an RL policy that learns `ls -t`. A prompt mentioning timestamps was out of scope by design.
- **Model and prompt.** There is a single cheap model (`deepseek-v4.1-flash-1017`, provider pinned) and a single prompt. Stronger models or other scaffolds may explore differently.
- **Nondeterminism.** Temperature 0 was not deterministic: 15/73 pairs were discordant with no causal mechanism visible (no time-based command anywhere). That noise floor limits power.
- **NORM side effects.** Normalization makes the git index stat-dirty and can change build tools' rebuild decisions. Validation showed no grade change at base, and NORM passed about as often as ORIG. Only `cwd` was normalized. Copies elsewhere on disk (site-packages, caches) keep their times. Directory mtimes were normalized too.
- **Selection.** The image-size cap (≤ 1.2 GB) excluded 135 flagged tasks, which skews toward smaller repos. The extension was decided after an interim look, but it used a fixed stopping rule and is reported as secondary.
- **Protocol amendments.** There were four, all made blind to the outcome under comparison and documented. Pilot v1 is excluded.
- **Submit detection.** The loop stopped only on a bare `echo SUBMIT`, so some runs continued after `cd … && echo SUBMIT`. This applies equally to both conditions, and the final state was graded regardless. An "effective steps" metric is reported in `results/report_tables.md`.
- **File-open heuristic.** "Files opened" is a heuristic (command tokens that resolve to candidate paths).

## 7. Informed agent (added 2026-10-20; earlier sections unchanged)

**Question.** Does the leak help an agent that is *told* to look at modification times? This stands in for an RL policy that has learned `ls -t`.
**Pre-registration:** `results/informed_plan.md`, written before any agent call, with 2 dated amendments. Both amendments are descriptive only; the protocol never changed.
**Code (new files only):** `scripts/agent_informed.py`, `orclient_informed.py`, `stepB_informed.py`, `informed_order.py`, `informed_analyze.py`, `informed_report_tables.py`.
**Data:** `results/informed_runs.jsonl`, `informed_state.json`, `informed_log.txt`, `informed_analysis.json`, `informed_cmd_audit.json`, `informed_hygiene.json`, `spend_informed.jsonl`, and `runs/<task>/INF-{ORIG,NORM}/`.
**Full tables:** `results/informed_report_tables.md`. Every number below comes from these files.

### 7.1 Verdict (plain English)
1. **Telling the agent about the trick did not make the leak measurably useful.**
   - Same day, same hint, timestamps intact vs normalised (INF-ORIG vs INF-NORM):
     - pre-registered primary 30: **20 vs 17**, discordant 7:4, exact McNemar **p = 0.55**, difference **+10.0 pp (95% CI −10.0 to +30.0)**;
     - all 73: **50 vs 45**, 14:9, **p = 0.40**, **+6.85 pp (−5.5 to +19.2)**.
   - The point estimates are positive and a little larger than in the uninformed Step B (+3.3 pp / +4.1 pp). The intervals are wide and include 0.
2. **The hint did not change the pass rate.**
   - INF-ORIG vs the Step-B ORIG runs: primary 20 vs 21 (p = 1.0, −3.3 pp, CI −20.0 to +13.3); all 73: **50 vs 50** (8:8, p = 1.0, 0.0 pp, CI −11.0 to +11.0).
   - Secondary, INF-NORM vs NORM: 45 vs 47 (p = 0.83, −2.7 pp, CI −15.1 to +9.6).
3. **The agent followed the hint only partly and shallowly.** That is the main limitation of the result.
   - Only **27/73 INF-ORIG runs** (37%) and **24/73 INF-NORM runs** ran a time-based command before the first edit. Uninformed ORIG did so in 1/73, the `stat` false positive from Step B.
   - In 23 of the 27 INF-ORIG runs, the only time-based commands were `ls -t`-type listings, almost always a single top-level `ls -lt`. That ranks top-level entries (mostly directories), not the files of the late cluster.
   - Only **4/73** INF-ORIG runs used a file-level `find -newer/-mtime/-mmin`.
   - Post hoc and descriptive (Amendment 2): a late-cluster file appeared in the first 10 output lines of the first time-based command in 11/27 INF-ORIG runs vs 6/25 INF-NORM runs.
   - So the experiment tests a *weakly* informed agent. It is not a policy that exploits the leak fully. Step A's offline numbers (hit@1 0.92 for the upstream-fix files) remain the upper bound on what the signal offers.
4. **Why the gain is small even when the agent looks (inference from the run data):** the issue text already leads this agent to the late cluster.
   - A late-cluster file was opened before the first edit in 71/73 INF-ORIG runs and 72/73 INF-NORM runs (Step B: 71/73 and 72/73).
   - So file localisation, the only thing this leak reveals (I2), is rarely the bottleneck for these tasks.
   - Observational (INF-ORIG): runs that ran a time-based command before the first edit passed 20/27; INF-NORM passed 17/27 on the same tasks and Step-B ORIG 19/27. Runs that did not passed 30/46 (INF-NORM 28/46, ORIG 31/46). Compliance is not randomised, so this is not causal.
5. **Severity: keep Low (I2/R4). Do not move it to Medium on this evidence.** Give "Low" a stated upper bound:
   - With the hint, the all-pairs CI still allows up to about **+19 pp**, so a Medium-sized benefit is not ruled out.
   - The agent rarely used the leak the way an optimised policy would (recursive `find -newer`, `ls -lt` inside the right package).
   - **What would move it to Medium:** an agent or policy that performs file-level time-ranking in most runs and gains a pass-rate advantage over its own normalised control. That can be tested with a stronger model, or with a scaffold that runs `find . -newer <anchor>` automatically. Neither was done here.

### 7.2 Method (differences from Step B only)
- **Hint.** One line appended to the Step-B system prompt, verbatim: *"Tip: files that were modified recently relative to the rest of the repository often indicate where a change belongs, so early on it can help to run `ls -lt` or `find . -newer <some file>` to see them."*
  - Everything else is identical to Step B: model `deepseek/deepseek-v4.1-flash-1017`, provider pinned to `deepseek` with no fallbacks, temperature 0, seed 7, max_tokens 8192, step cap 40, $0.15 per-run cap, truncation, DSML parsing, images, container flags, grader.
  - The agent loop was diffed against `agent.py`. The only other differences are the spend file and a per-step disk check.
- **Conditions.**
  - INF-ORIG: the no-op prep from Step B.
  - INF-NORM: every mtime under `cwd` set to the epoch. Verification returned 0 newer entries in 73/73 runs, as in Step B.
  - Condition order was set by a new seeded coin (seed **20261020**); 37/73 tasks started with INF-ORIG.
- **Tasks.** Exactly the 73 Step-B pairs, in Step-B processing order, primary 30 first (`results/informed_order.json`). Step-B validation was reused.
- **Pilot.** The pilot pair (task 002739) had no protocol change and is included, as pre-registered.
  - Its INF-ORIG run degenerated into repeated DSML markup (19 format errors). This model failure mode also occurred in Step B: 3 ORIG runs had ≥ 10 format errors.
- **Amendments.**
  - Amendment 1 adds a descriptive "time command written in the reply but not executed" count. Example: one reply contained both a ```bash `ls` ``` block and a DSML `ls -lt`; the unchanged parser ran `ls`.
  - Amendment 2 adds the post-hoc "late file surfaced" metric. Its addendum was decided after seeing that the loose variant fires equally in INF-NORM.
- **Stopping rules.** Never triggered: no new task at ≥ $3.55, no new run at ≥ $3.70, hard stop at $4.00, disk ≥ 20 GB, deadline 2026-10-21T06:00Z. All 73 pairs completed.
- **Optional stronger-model arm: not run.** The pre-registered condition was spend ≤ $2.90 after the main runs; actual spend was $3.5783, leaving too little budget for a meaningful number of pairs.

## 8. Scaffold arm (forced compliance) (added 2026-10-21; earlier sections unchanged)

**Question.** Section 7 measured whether a cheap agent *followed a hint*. Only 27/73 runs ran a time-based command, so that study measured compliance. Here compliance is taken out: **the harness itself** runs a fixed mtime-ranking command in the container before the first model call and puts its output into the first user message. The agent always sees the ranked late cluster under ORIG.
**Pre-registration:** `results/scaffold_plan.md`, written before any agent call, plus Amendment 1 (descriptive only; protocol never changed).
**Code (new files only):** `scripts/scaffold_cmd.py`, `scaffold_offline_check.py`, `scaffold_order.py`, `orclient_scaffold.py`, `agent_scaffold.py`, `stepB_scaffold.py`, `scaffold_analyze.py`, `scaffold_posthoc.py`, `scaffold_hygiene.py`, `status_tick_scaffold.py`.

### 8.1 Verdict (plain English)
1. **Pre-registered decision rule:** SCF-ORIG minus SCF-NORM on all 73 pairs is **+12.3 pp** (51 vs 42; discordant 18:9; exact McNemar p = 0.12; paired bootstrap 95% CI **−1.4 to +26.0 pp**).
   - That is below the +15 pp threshold, so **Low stands**, now without the "cheap model's habits" caveat: the agent was guaranteed to see the ranking.
   - **Upper bound:** the CI does not exclude a benefit of up to about **+26 pp** for this model and scaffold.
2. **The primary 30 look stronger:** 22 vs 13, discordant 12:3, **p = 0.035**, +30.0 pp (CI +6.7 to +53.3).
   - The difference is concentrated in the strong stratum: all 73, strong 26 vs 17 (+24.3 pp, CI +2.7 to +46.0, p = 0.064); random 25 vs 25.
   - The decision rule names all 73, and it is applied as written.
3. **Most of the ORIG−NORM gap comes from SCF-NORM doing badly, not from SCF-ORIG doing well.** These are cross-day comparisons; temperature 0 is not deterministic here.
   - **SCF-ORIG matches the runs without a scaffold:**
     - vs Step-B ORIG: 51 vs 50 (11:10, p = 1.0, +1.4 pp, CI −11.0 to +13.7);
     - vs INF-ORIG: 51 vs 50 (13:12, p = 1.0, +1.4 pp, CI −12.3 to +15.1).
   - **SCF-NORM is the lowest of the three NORM-type conditions:**

     - the empty listing may itself hurt the agent;
     - the low SCF-NORM count may be chance.
   - The SCF-NORM vs NORM interval includes 0, so neither can be excluded.
4. **Where the leak does show up, it is in efficiency, not in finding the right file.** Paired SCF-ORIG − SCF-NORM, all 73:

5. **Recommendation:** keep **Low (I2/R4)**.
   - The forced-compliance arm did not reach the pre-registered +15 pp on all 73. The point estimate (+12.3 pp) sits close to the threshold, and the CI allows up to +26 pp.
   - The positive estimate rests on a control whose pass rate fell below its untreated counterpart, so it should not be read as a clean "leak value".
   - A stricter design would compare SCF-ORIG with a NORM control that shows a non-empty but uninformative list. It would also use a stronger model and more tasks; per §3.2, 80% power at about +15 pp needs more than 73 pairs at this discordance.

### 8.2 Method (differences from Step B only)
- **Scaffold.**
  - After the condition's timestamp prep, the harness runs one fixed command via `docker exec` in `cwd`. It is not an agent step.
  - Its literal output is appended to the first user message under the header `Files in the repository ranked by last-modified time (most recent first):`, inside `<output>…</output>`.
  - There is no hint line; the system prompt and task text are those of Step B.
  - Model, provider pin, temperature 0, seed 7, max_tokens 8192, the step cap (40), the $0.15 per-run cap, truncation, DSML parsing, images, container flags, the grader and reused Step-B validation are all unchanged.
- **Rule ANCHOR_EXCL** (`scripts/scaffold_cmd.py`; the verbatim command is in the plan):
  - Candidates are regular files under `cwd`. `.git` and the Step-A tracked-proxy artefact directories and extensions (`node_modules`, venvs, caches, `__pycache__`, `*.egg-info`, `*.pyc`, …) are pruned.
  - Anchor = the most common whole-second mtime among the candidates (the bulk checkout cluster).
  - Files strictly newer than the anchor are listed newest first, up to 30 lines, each `YYYY-MM-DD HH:MM:SS  path`.
- **Offline check before any agent call** (`results/scaffold_offline_check.json`, 73 tasks' manifests):
  - The rule puts a late-cluster file at rank 1 with expected hit@1 0.986, and an upstream-fix file at rank 1 with hit@1 0.941 (17 anchored tasks). Step A gets 0.941 on the same 17 tasks and 0.92 overall.
  - The spec-literal variant without the artefact exclusions scores late hit@1 0.904. In 6/73 tasks, `node_modules`/`.venv` files installed after the late cluster push it out of the top 30, so the Step-A exclusions are part of the rule (documented decision).
- **In-container check** (`results/scaffold_container_check.json`, task 002739, no agent): ORIG gave 29 lines with the two late files at ranks 1–2, as offline; NORM gave empty output.
- **Live:**
  - SCF-ORIG output was never empty. A late-cluster file was at rank 1 in **72/73** runs, and the median list length was 4 lines (6 runs hit the 30-line cap).
  - **SCF-NORM showed the header and an empty `<output>` block in 73/73 runs**: every mtime is the epoch, so no file is newer than the anchor. Nothing was substituted, and NORM verification returned 0 newer entries in 73/73 runs.
- **Order:** the same 73 tasks in the same order as §7 (primary 30 first). Condition order was set by a new coin with **seed 20261021**; 46/73 tasks started with SCF-ORIG.
- **Pilot:** task 002739 ran with no protocol change and is included.
- **Interim look:** an unplanned look at 24 pairs (a pipeline test) is disclosed in Amendment 1. Nothing was changed after it.
- **Stopping rules:** none triggered (new task < $3.55, new run < $3.70, hard $4.00, disk ≥ 20 GB, deadline 2026-10-22T06:00Z). All 73 pairs completed.

### 9.4 Caveats
- **Budget amendment.** The first loop stopped after task 66 at **$1.8538**, at the original new-run threshold ($1.85 of a $2.00 cap), because SCF-SHAM runs cost more than planned. ## 10. Public summary (draft)

*Cupel — MiMo `mtime_scope` side channel. All numbers are from `results/` (`sham_analysis_all_available.json`, `scaffold_analysis.json`, `stepA_metrics.json`/`stepA_per_task.jsonl`).*

- **The fix holds.** Normalising timestamps under the repository removed the signal in every run checked: 292/292 NORM-prepared runs had no file newer than the epoch, and the harness's ranking command then returned an empty list in 73/73 SCF-SHAM runs (73/73 in SCF-NORM).
- **The side channel is present in 85% of tasks** (256 of 300 scanned images flagged `mtime_scope`). In the 73 agent-tested tasks, ranking files by mtime put a file from the late (upstream-change) cluster first in 72/73.
- **An agent forced to see the ranking reaches the right file sooner, but solves no more tasks.** Against a matched control that saw a same-length list of random files:
  - its first edit came **3.1 steps sooner** (95% CI 1.2–5.0);
  - **step-cap stops went from 20 to 11** (of 73);
  - cost per solved task fell from $0.0405 to $0.0264.
- **Correctness gain: not detected.** 51 vs 51 solved of 73 (0.0 pp); the 95% upper bound is **+12.3 pp**. An earlier apparent gain (+12.3 pp) came from a control that showed an empty list.
- **The effect is strongest on tasks with a short source-containing late cluster that overlaps the tests** (1–10 late files):
  - first edit 3.2 steps sooner (CI 1.2–5.3);
  - 4.7 fewer steps (CI 0.2–9.3);
  - 37 tasks, solve rate 26 vs 24.
  - On the other 36 tasks the speed-up was 3.0 steps (CI −0.1 to 6.3).
- **Severity: Low** (information I2, reachability R4) for present-day agents. The information content is high (Step A: an upstream-fix file ranked first in 92% of anchored tasks), so an agent trained to read mtimes would gain a localisation shortcut.
- **Remedy:** normalise timestamps when building images, e.g. `find <repo> -exec touch -h -d @0 {} +`.

**Per-task severity buckets:** `results/sham_task_buckets_all_available.csv` (73 tasks; Higher = 1–10 late files with ≥ 1 source file: 70, solved 49 SCF-ORIG vs 48 SCF-SHAM; Low: 3, solved 2 vs 3). Because most tested tasks have small late clusters, the strong-stratum flag in the same file (late cluster overlaps the test patch or upstream fix: 37 tasks) is the more discriminating marker in this sample.
